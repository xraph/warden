When running with the Forge extension (or using `api.New()` directly), Warden exposes a REST API for managing authorization entities.

## Authorization Check

### POST /v1/authz/check

Check if a subject is authorized to perform an action.

**Request:**
```json
{
  "subject_kind": "user",
  "subject_id": "user-42",
  "action": "read",
  "resource_type": "document",
  "resource_id": "doc-123",
  "context": {
    "ip_address": "10.0.1.5"
  }
}
```

**Response (200):**
```json
{
  "allowed": true,
  "decision": "allow",
  "reason": "rbac: permission document:read granted",
  "sources": ["rbac"]
}
```

### POST /v1/authz/enforce

Same as check, but returns 403 if denied.

### POST /v1/authz/batch-check

Check multiple authorization requests in one call.

**Request:**
```json
{
  "checks": [
    {"subject_kind": "user", "subject_id": "user-42", "action": "read", "resource_type": "document"},
    {"subject_kind": "user", "subject_id": "user-42", "action": "delete", "resource_type": "document"}
  ]
}
```

**Response (200):**
```json
{
  "results": [
    {"allowed": true, "decision": "allow", "reason": "rbac: granted"},
    {"allowed": false, "decision": "deny", "reason": "default deny"}
  ]
}
```

## Roles

| Method | Path | Operation |
|--------|------|-----------|
| `POST` | `/v1/roles` | Create role |
| `GET` | `/v1/roles/:roleId` | Get role |
| `PUT` | `/v1/roles/:roleId` | Update role |
| `DELETE` | `/v1/roles/:roleId` | Delete role |
| `GET` | `/v1/roles` | List roles |
| `POST` | `/v1/roles/:roleId/permissions` | Attach permission |
| `DELETE` | `/v1/roles/:roleId/permissions/:permissionId` | Detach permission |

### Create Role

```json
POST /v1/roles
{
  "name": "Editor",
  "slug": "editor",
  "description": "Can read and write documents",
  "parent_slug": "viewer",
  "is_default": false,
  "metadata": {"tier": "premium"}
}
```

`parent_slug` must name a role in the same namespace, and it cannot be the role itself or one of its descendants, since that would make the role its own ancestor. On create that rules out the role's own slug, and also a parent whose chain of parents already leads to the new slug: a role can name a parent slug before any role holds it, so the chain can be waiting for the role you're creating. On update (`PUT`) it rules out the role and everything below it. Either refusal is 400 and writes nothing. An empty `parent_slug` on update clears the parent.

A system role cannot be changed through REST: `PUT` and `DELETE` on one, and attaching or detaching a permission on one, are 403 with the message `"<name>" is a system role and cannot be changed or deleted`, and nothing is written. Assigning a system role to a subject is still allowed. The dashboard refuses the same writes with the same message.

### Attach and Detach a Permission

```json
POST /v1/roles/:roleId/permissions
{
  "permission_name": "document:read",
  "permission_namespace_path": ""
}
```

You can name the permission by `permission_name` (with `permission_namespace_path`, empty for the tenant root) or by `permission_id`. The name wins when you send both. The permission has to exist: an attach of a name with no permission in that namespace is 404 with the message `no permission named <name> in that namespace`, and an unknown `permission_id` is 404 too. Nothing is attached either way.

`DELETE /v1/roles/:roleId/permissions/:permissionId` takes the permission by ID in the path, or by name through the `permission_name` and `permission_namespace_path` query parameters, which win over the path. A detach of a grant the role does not hold is 404 with the message `<role name> does not grant <permission name>`. That includes a name in the wrong namespace, which earlier releases answered with 204 while the grant stayed. The dashboard refuses the same attach and detach with the same messages.

## Permissions

| Method | Path | Operation |
|--------|------|-----------|
| `POST` | `/v1/permissions` | Create permission |
| `GET` | `/v1/permissions/:permissionId` | Get permission |
| `DELETE` | `/v1/permissions/:permissionId` | Delete permission |
| `GET` | `/v1/permissions` | List permissions |

### Create Permission

```json
POST /v1/permissions
{
  "name": "Read Documents",
  "resource": "document",
  "action": "read",
  "description": "Allows reading documents"
}
```

`DELETE` on a system permission is 403 with the message `"<name>" is a system permission and cannot be changed or deleted`, and nothing is deleted. `DELETE` on a permission any role still grants is 409 with the message `<name> is still granted by <role slugs>. Detach it from those roles first.`, and nothing is deleted. The store's delete would also remove the grant from every role that holds it, system roles included, so you detach it on purpose first. The dashboard refuses the same delete with the same message.

The action may not contain `:`. The engine joins resource and action with `:` when it checks a grant, so `(warden, role:manage)` and `(warden:role, manage)` would be the same permission. A request whose action has one is 400 and writes nothing. The resource may contain `:` (`warden:role`), and `*` is still a valid action. A permission stored with `:` in its action before this rule still reads, checks and deletes.

## Relations

| Method | Path | Operation |
|--------|------|-----------|
| `POST` | `/v1/relations` | Write relation tuple |
| `POST` | `/v1/relations/delete` | Delete relation tuple |
| `GET` | `/v1/relations` | List relation tuples |

### Write Relation

```json
POST /v1/relations
{
  "object_type": "document",
  "object_id": "doc-123",
  "relation": "viewer",
  "subject_type": "user",
  "subject_id": "user-42"
}
```

REST writes every tuple at the tenant root: the request has no namespace field. When a resource type named after `object_type` is declared at the tenant root, the tuple must name a relation it declares and a subject that relation allows (`user` for `user:...`, `group#member` for a subject set; a relation that lists no subject types allows any). Otherwise the response is 400 with a message naming the tuple, the resource type and what it allows, and nothing is written. An object type with no resource type at the tenant root is not checked. Add `"subject_relation": "member"` to write a subject set such as `group:eng#member`.

### Delete Relation

```json
POST /v1/relations/delete
{
  "object_type": "document",
  "object_id": "doc-123",
  "relation": "viewer",
  "subject_type": "group",
  "subject_id": "eng",
  "subject_relation": "member"
}
```

The delete removes the tuple whose key matches every field: `namespace_path` (left out or empty means the tenant root), the object, the relation, the subject and `subject_relation`. An empty or missing `subject_relation` names the direct tuple. So with `group:eng` and `group:eng#member` both stored, a delete without `subject_relation` removes `group:eng` and leaves `group:eng#member`, and the request above removes `group:eng#member` and leaves `group:eng`. Earlier releases left `subject_relation` out of the delete's key, so a delete of `group:eng` could also remove `group:eng#member`. The response is 204 whether or not a tuple matched.

## Policies

| Method | Path | Operation |
|--------|------|-----------|
| `POST` | `/v1/policies` | Create policy |
| `GET` | `/v1/policies/:policyId` | Get policy |
| `PUT` | `/v1/policies/:policyId` | Update policy |
| `DELETE` | `/v1/policies/:policyId` | Delete policy |
| `GET` | `/v1/policies` | List policies |

### Create Policy

```json
POST /v1/policies
{
  "name": "Office Hours Only",
  "effect": "deny",
  "priority": 10,
  "is_active": true,
  "subjects": ["*"],
  "actions": ["write"],
  "resources": ["document:*"],
  "conditions": [
    {"field": "context.hour", "operator": "gte", "value": 18}
  ]
}
```

## Error Responses

A 4xx response carries the status as a number in `code` and the message in `error`:

```json
{
  "code": 404,
  "error": "no permission named document:read in that namespace"
}
```

A 422 has `"error": "Validation failed"` and adds a `validationErrors` list, one entry per field with `field` and `message`, plus `value` and `code` when they are set. A 500 is different: `code` is the string `INTERNAL_SERVER_ERROR` and `message` is `Internal Server Error`, unless the app exposes internal errors, in which case `message` holds the error text.

| Status | Meaning |
|--------|---------|
| 400 | Bad request: a body that does not bind or leaves out a field the request requires, an invalid ID, timestamp or namespace path, a missing tenant, a parent role that does not exist or that would make the role its own ancestor, a permission action that contains `:`, or a relation tuple its resource type does not declare |
| 401 | Authentication required |
| 403 | Forbidden (authorization denied, an AuthZEN context naming another tenant or namespace, or a change to a system role or system permission) |
| 404 | Entity not found, including a permission an attach names that does not exist and a grant a detach names that the role does not hold |
| 409 | Conflict (a role, permission, policy, resource type, role assignment or relation tuple that already exists in its scope, including a policy renamed onto a name another policy holds in the same namespace, a record or policy that changed since the request read it, a role whose member cap the request would exceed or lower below its members, or a permission delete while a role still grants it) |
| 422 | A well-formed body that fails validation, for example an empty relation field, an unknown policy effect or subject kind, a policy condition with an unknown operator or field or a value that is not a list, or an empty or oversized batch |
| 500 | Anything else, including a store failure |
