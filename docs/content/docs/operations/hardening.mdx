---
title: Hardening
description: Running Warden's management API safely in production.
---

Warden's management API can grant roles, write relation tuples, and read the audit log. Treat it like any other privileged admin surface: TLS in front of it, authentication on, and the fewest routes exposed that your deployment actually needs.

## Put TLS at the host, not in Warden

Warden doesn't terminate TLS itself: the `api.API` handler is a plain `http.Handler` mounted on `forge.Router`. Terminate TLS at your load balancer, ingress, or reverse proxy in front of the Forge app, the same way you would for any other Forge route. Never expose the `base_path` (default `/warden`) over plaintext HTTP outside a network you fully control.

## Keep authentication on

`auth.require_identity` defaults to `true`: every route under `base_path` gets `401` for an unauthenticated caller and `403` for one without the mapped permission (`warden:<entity>` + `manage`/`read`/`check`/`read_audit`; see [Forge Extension](/docs/integration/forge-extension#rest-api-endpoints)). Leave it on in production.

Setting it to `false` is refused unless you also call `extension.WithInsecureAllowUnauthenticatedRoutes()`:

```go
wardenext.New(
    wardenext.WithConfig(wardenext.Config{
        Auth: wardenext.AuthConfig{RequireIdentity: false},
    }),
    wardenext.WithInsecureAllowUnauthenticatedRoutes(),
)
```

That option exists for local development and test harnesses, not production: without an identity check, any network peer that can reach `base_path` could grant itself roles or read the audit log. If you need an open check endpoint for a trusted internal caller, use the narrower `auth.allow_anonymous_checks: true` instead: it only opens `/v1/authz/check`, `/v1/authz/enforce`, and `/v1/authz/batch-check`, and every other route still requires identity.

## Grant yourself access with BootstrapAdmin

Because authentication is on by default, a freshly registered extension has no role holder: nobody can call the management API until something grants a role. Call `Extension.BootstrapAdmin(ctx, tenantID, subject)` once per tenant, right after `Start`, to create the idempotent `warden-admin` system role and assign it to a known subject (see [Forge Extension](/docs/integration/forge-extension#granting-yourself-access-bootstrapadmin)). Do this from a deploy step or an init container you control, not from an open route.

## SDK-only deployments: disable_routes

If your application only ever calls the engine in-process (`eng.Check`, middleware) and never needs the HTTP management API, set `disable_routes: true`. That removes the entire attack surface of the management API: there's nothing to authenticate against because nothing is mounted:

```yaml
extensions:
  warden:
    disable_routes: true
```

## Lock down declarative apply in production

If you use the `.warden` DSL with `declarative_on_start: true`, also set `declarative_strict: true` in production:

```yaml
extensions:
  warden:
    declarative_on_start: true
    declarative_strict: true
```

With `declarative_strict: false` (the default), a bad `.warden` source logs a warning and the extension starts anyway. That's convenient in development, but it means a broken or malicious config change can silently fail to apply while the app keeps running on stale state. `declarative_strict: true` turns that into a startup failure instead, so a bad apply is caught by your deploy pipeline rather than discovered later as "why doesn't this permission exist."

## Separate migrations from application startup

`disable_migrate` defaults to `false`, which means every replica that starts runs `store.Migrate(ctx)` before serving traffic. That's fine for a single instance or a dev environment, but in a multi-replica production deployment, running schema migrations from N concurrently-starting replicas is unnecessary contention against the migration lock table. Set `disable_migrate: true` and run migrations as a separate, single step in your deploy pipeline instead:

```yaml
extensions:
  warden:
    disable_migrate: true
```

Use the `warden` CLI with `WARDEN_STORE_DSN` set to the same DSN your app connects with:

```bash
export WARDEN_STORE_DSN="postgres://user:pass@host/db"
warden apply -f ./config.warden --store "$WARDEN_STORE_DSN"
```

`warden apply` runs the store's migrations before applying (pass `--skip-migrate` to skip that and only apply). Prefer `WARDEN_STORE_DSN` over `--store` for a Postgres DSN specifically, so the password doesn't land in shell history or show up in `ps`. See [Upgrades and migrations](/docs/operations/upgrades-and-migrations) for the full migration story.

## Network placement of the database

The store backends (`store/postgres`, `store/sqlite`, `store/mongo`) connect directly to your database with no built-in network policy of their own. That's your infrastructure's job. Put the database on a private network reachable only from the application tier, not the public internet, and use `postgres.WithStatementTimeout` (see [Upgrades and migrations](/docs/operations/upgrades-and-migrations)) to bound how long a single query can hold a connection.

## Summary checklist

- TLS terminated in front of the app, never plaintext `base_path` outside a trusted network.
- `auth.require_identity: true` (the default); reach for `WithInsecureAllowUnauthenticatedRoutes()` only in development.
- `BootstrapAdmin` called from a controlled deploy step, not an open route.
- `disable_routes: true` if you never need the HTTP management API.
- `declarative_strict: true` if you use declarative apply in production.
- `disable_migrate: true` plus a separate `warden apply`/migrate step, for multi-replica deployments.
- Database on a private network, with a statement timeout configured.
