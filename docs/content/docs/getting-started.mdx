## Installation

### Library

```bash
go get github.com/xraph/warden
```

### CLI (`warden` and `warden-lsp`)

The `warden` CLI applies `.warden` configs to a store; `warden-lsp` powers the editor extensions. Three options:

<Tabs items={["go install", "Pre-built binary", "From source"]}>

```bash tab="go install"
go install github.com/xraph/warden/cmd/warden@latest
go install github.com/xraph/warden/cmd/warden-lsp@latest
```

```bash tab="Pre-built binary"
# Pick a platform from https://github.com/xraph/warden/releases/latest
curl -L -o warden.tar.gz \
  https://github.com/xraph/warden/releases/latest/download/warden-<version>-<os>-<arch>.tar.gz

# Verify the checksum
curl -L -o checksums.txt \
  https://github.com/xraph/warden/releases/latest/download/checksums.txt
shasum -a 256 -c checksums.txt --ignore-missing

tar -xzf warden.tar.gz
sudo mv warden warden-lsp /usr/local/bin/
warden version
```

```bash tab="From source"
git clone https://github.com/xraph/warden.git
cd warden
make build
./bin/warden version
```

</Tabs>

Each pre-built archive contains both `warden` and `warden-lsp`. Available for `linux`, `darwin` and `windows`, each on `amd64` and `arm64`.

### VS Code extension

```bash
code --install-extension xraph.vscode-warden
```

The extension provides syntax highlighting, completion, hover, go-to-definition, and live diagnostics for `.warden` files. See the [DSL tooling guide](./integration/dsl-tooling) for editor configuration.

You need Go 1.26 or later.

## Step 1: Create a Store and a Tenant Context

Warden needs a store to persist roles, permissions, policies, relations, and assignments. Start with the in-memory store for development. Every check is scoped to a tenant, and a check with no tenant fails with `ErrTenantRequired` unless you turn `RequireTenant` off, so put one on the context:

```go
import (
    "context"

    "github.com/xraph/warden"
    "github.com/xraph/warden/store/memory"
)

ctx := warden.WithTenant(context.Background(), "docs-app", "acme")
st := memory.New()
```

Under Forge you don't need `WithTenant`: Warden reads the tenant from `forge.Scope`.

## Step 2: Create the Engine

```go
eng, err := warden.NewEngine(
    warden.WithStore(st),
)
if err != nil {
    log.Fatal(err)
}
```

## Step 3: Create a Role and Permission

```go
import (
    "github.com/xraph/warden/permission"
    "github.com/xraph/warden/role"
)

// IDs are auto-assigned by the store on Create. The in-place mutation
// means r.ID is populated when the call returns, which AttachPermission
// below needs.

// Create a permission
if err := st.CreatePermission(ctx, &permission.Permission{
    TenantID: "acme",
    Name:     "document:read",
    Resource: "document",
    Action:   "read",
}); err != nil {
    log.Fatal(err)
}

// Create a role
r := &role.Role{TenantID: "acme", Name: "Viewer", Slug: "viewer"}
if err := st.CreateRole(ctx, r); err != nil {
    log.Fatal(err)
}

// Attach permission to role
if err := st.AttachPermission(ctx, "acme", r.ID, permission.Ref{Name: "document:read"}); err != nil {
    log.Fatal(err)
}
```

## Step 4: Assign the Role

```go
import "github.com/xraph/warden/assignment"

if err := st.CreateAssignment(ctx, &assignment.Assignment{
    TenantID:    "acme",
    RoleID:      r.ID,
    SubjectKind: "user",
    SubjectID:   "user-42",
}); err != nil {
    log.Fatal(err)
}
```

These writes go straight to the store. That's fine while there's no cache. Once you configure one, a direct store write doesn't invalidate it (only the API, the dashboard and the DSL applier fire the hooks that do), so call `eng.InvalidateTenant` after writing to the store yourself.

## Step 5: Check Authorization

```go
result, err := eng.Check(ctx, &warden.CheckRequest{
    Subject:  warden.Subject{Kind: warden.SubjectUser, ID: "user-42"},
    Action:   warden.Action{Name: "read"},
    Resource: warden.Resource{Type: "document", ID: "doc-123"},
})
if err != nil {
    log.Fatal(err) // Check fails closed: an error means no decision
}

if result.Allowed {
    fmt.Println("Access granted!")
} else {
    fmt.Println("Access denied:", result.Reason)
}
```

`eng.CanI(ctx, warden.SubjectUser, "user-42", "read", "document", "doc-123")` is the one-line boolean form, and `eng.Enforce` returns an error on deny.

## Step 6: Add ABAC Policies (Optional)

A policy matches on subjects, actions and resources, then checks its conditions against the request. Condition fields are dotted paths: `subject.kind`, `subject.id`, `subject.attributes.<k>`, `resource.type`, `resource.id`, `resource.attributes.<k>`, `action.name` and `context.<k>`.

```go
import "github.com/xraph/warden/policy"

p := &policy.Policy{
    TenantID:  "acme",
    Name:      "Block deletes from outside the office network",
    Effect:    policy.EffectDeny,
    Actions:   []string{"delete"},
    Resources: []string{"document:*"},
    Conditions: []policy.Condition{{
        Field:    "context.network",
        Operator: policy.OpNotEquals,
        Value:    "office",
    }},
    IsActive: true,
}
if err := st.CreatePolicy(ctx, p); err != nil {
    log.Fatal(err)
}
```

Pass the value in the check with `Context: map[string]any{"network": "home"}`. An explicit deny from a policy wins over any allow. For a time window, set `NotBefore` and `NotAfter` on the policy; the `time_before` and `time_after` operators compare RFC 3339 timestamps.

## Step 7: Add ReBAC Relations (Optional)

```go
import "github.com/xraph/warden/relation"

if err := st.CreateRelation(ctx, &relation.Tuple{
    TenantID:    "acme",
    ObjectType:  "document",
    ObjectID:    "doc-123",
    Relation:    "viewer",
    SubjectType: "user",
    SubjectID:   "user-42",
}); err != nil {
    log.Fatal(err)
}
```

On its own, a tuple grants only an action with the same name as its relation, so this one would grant `viewer` but not `read`. To map actions to relations, define a resource type with `permission read = viewer or owner` (in a `.warden` file or through the store) and give the engine an expression evaluator. The Forge extension wires one; standalone, pass `warden.WithExpressionEvaluator(dsl.NewEngineEvaluator(st))` to `NewEngine`. The [full example](/docs/guides/full-example) does exactly that. See [Relations & Tuples](/docs/authorization/relations-tuples).

## Step 8: Use with PostgreSQL

For production, switch to the PostgreSQL store:

```go
import (
    "github.com/xraph/grove"
    "github.com/xraph/grove/drivers/pgdriver"
    _ "github.com/xraph/grove/drivers/pgdriver/pgmigrate" // Migrate needs the executor
    "github.com/xraph/warden/store/postgres"
)

drv := pgdriver.New()
if err := drv.Open(ctx, "postgres://user:pass@localhost/warden"); err != nil {
    log.Fatal(err)
}
db, err := grove.Open(drv)
if err != nil {
    log.Fatal(err)
}

pgStore := postgres.New(db)
defer pgStore.Close()

// Run migrations
if err := pgStore.Migrate(ctx); err != nil {
    log.Fatal(err)
}

eng, err := warden.NewEngine(
    warden.WithStore(pgStore),
)
```

## Step 9: Use the Declarative DSL (Optional)

Programmatic seeding works for examples, but production setups define roles, permissions, policies, and relations as source-controlled `.warden` files.

```bash
go install github.com/xraph/warden/cmd/warden@latest
```

```warden
// config/main.warden
warden config 1
tenant t1                              // optional, omit it for single-tenant apps

permission "doc:read"  (document : read)
permission "doc:write" (document : write)

role viewer {
  name   = "Viewer"
  grants = ["doc:read"]
}

role editor : viewer {
  name   = "Editor"
  grants += ["doc:write"]
}
```

```bash
warden lint config/                       # static checks, no DB
warden apply -f config/ --store sqlite:./warden.db
```

The `tenant` declaration is optional. Single-tenant apps that never call `warden.WithTenant` should omit it: every entity lands in the global scope (`tenant_id = ""`), which is what the engine looks up at Check time too.

The same CLI ships a language server (`warden lsp`) used by the VS Code extension and Neovim/Helix configs for diagnostics, completion, hover, and go-to-definition. See [DSL & Tooling](/docs/integration/dsl-tooling).

### Or embed the config

If you'd rather ship the config inside your binary instead of distributing files alongside it, use `//go:embed` and `dsl.ApplyFS`:

```go
//go:embed all:config
var configFS embed.FS

func main() {
    eng, _ := warden.NewEngine(warden.WithStore(memory.New()))

    _, err := dsl.ApplyFS(ctx, eng, configFS, "config",
        dsl.ApplyOptions{TenantID: "acme"},
        dsl.WithVariables(dsl.Variables{"REGION": os.Getenv("AWS_REGION")}),
    )
    if err != nil {
        log.Fatal(err)
    }
}
```

Same load-resolve-apply pipeline as the CLI, exposed as a library. Full reference and a runnable example: [DSL & Tooling: Programmatic apply](/docs/integration/dsl-tooling#programmatic-apply).
